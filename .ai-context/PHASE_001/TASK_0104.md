## 2. Problem

The current main phase implementation (`GameJudge.ExecuteMainPhase`) gives each player one action opportunity then moves on. This doesn't match the MTG priority system:

- Active player should be able to cast multiple spells per phase
- Opponent should get a response window after each spell
- Stack should only resolve when both players pass in succession
- Phase only ends when both pass with an empty stack

The `ActionJudge.ShouldResolveStack()` partially handles "both pass → resolve" but the outer loop in `ExecutePerformingActionStep` doesn't iterate correctly.

## 3. Acceptance Criteria

- [ ] Active player gets priority at start of each phase (RX-117.3a)
- [ ] Player with priority can take an action or pass
- [ ] After an action: opponent gets priority (response window)
- [ ] Both pass in succession with non-empty stack → top of stack resolves → active player gets priority (RX-117.4)
- [ ] Both pass in succession with empty stack → phase/step ends (RX-405.5)
- [ ] A player can cast multiple spells in a single main phase
- [ ] Before any player receives priority, the pre-priority procedure runs: check state-based actions repeatedly until none are performed, then (Phase 4) queue triggers — repeat until stable (RX-117.5)
- [ ] A state-based-action checker seam exists (a `PROCESSING_SBAS` state) that the Phase 4 checklist expansion (TASK_0402) extends without altering this loop
- [ ] Minimal SBA set implemented for the current pool: player at 0 life loses (RX-704.5a), creature with 0 toughness to graveyard (RX-704.5c/f), creature with lethal damage destroyed (RX-704.5g)
- [ ] Combat-damage death routes through the SBA checker, not inline in the combat step (coordinates with TASK_0102)
- [ ] Existing tests still pass (combat, land playing, etc.)

## 4. Implementation Guidance

The priority loop is essentially a state machine:

```
START → Active player has priority
  ├── Action taken → push to stack → Opponent gets priority
  │     ├── Opponent acts → push to stack → Active gets priority (loop)
  │     └── Opponent passes → Active gets priority
  │           ├── Active acts → push to stack → Opponent gets priority (loop)
  │           └── Active passes → RESOLVE top of stack → Active gets priority
  └── Pass → Opponent gets priority
        ├── Opponent acts → push to stack → Active gets priority (loop)
        └── Opponent passes → (stack empty? END : RESOLVE → loop)
```

- Refactor `ExecutePerformingActionStep` to implement this state machine
- The `ActionJudge.QueueAction` already handles stack resolution — the fix is in the outer loop
- Consider a `PriorityState` enum or tracking who passed last
- Key rules: RX-117.1 through RX-117.4, RX-405.5

### 4.1 State-Based Action Seam

- Implement the Rule 117.5 pre-priority procedure as a `PROCESSING_SBAS` state (see `PHASE_002/DESIGN_Engine_InteractionLayer.md` §2.2 and §4). Grant priority only after SBAs reach a fixed point.
- Put the SBA check behind a seam (e.g., an injected checker) so Phase 4 `TASK_0402` can extend the checklist without touching this loop. This boundary is fixed by ADR-012: Phase 1 owns the seam plus the minimal set; Phase 4 owns the checklist expansion.
- Phase 1 implements only the SBAs the current pool can trigger: RX-704.5a (0 life → lose), RX-704.5c/f (0 toughness → graveyard), RX-704.5g (lethal damage → destroy).
- Route combat-damage death through the SBA checker so there is a single death path (coordinates with TASK_0102), not an inline destroy in the combat step.
