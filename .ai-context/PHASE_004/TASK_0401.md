## 2. Problem

The engine cannot react to game events. Triggered abilities ("when/whenever/at" — Rule 603) watch for an event, then go on the stack the next time a player would receive priority. They are the second half of the Rule 117.5 pre-priority procedure (`TASK_0104` builds the state-based-action half of that loop; this task builds the trigger half). Without triggers, most non-vanilla cards — enters-the-battlefield effects, attack triggers, death triggers — cannot exist.

## 3. Acceptance Criteria

- [ ] A triggered ability's condition is detected when its trigger event occurs (Rule 603.2)
- [ ] Triggered abilities are queued when they trigger, not placed on the stack immediately (Rule 603.3)
- [ ] Pending triggers are put on the stack the next time a player would receive priority, before that player gets priority (Rule 603.3, part of the 117.5 procedure)
- [ ] Multiple triggers are ordered APNAP: active player's triggers first (in an order they choose), then non-active player's (Rule 603.3b)
- [ ] The 117.5 procedure interleaves correctly with state-based actions: repeat SBAs until none, then put triggers on stack, then repeat the whole loop until stable (`TASK_0402` completes the SBA half)
- [ ] A triggered ability can have a target, chosen as it is put on the stack (reuses `TASK_0304`/`TASK_0305`)
- [ ] Unit test: an enters-the-battlefield trigger goes on the stack and resolves
- [ ] Unit test: two simultaneous triggers controlled by different players are ordered APNAP

## 4. Implementation Guidance

- Model a triggered ability distinct from an activated ability: it has a trigger condition (event predicate) and an effect. The ANTLR grammar parses "when/whenever/at" clauses into this shape (ADR-009 — all oracle text through the grammar).
- Add an event signal the engine already raises (or introduce a lightweight event hook) that trigger conditions subscribe to. On a matching event, enqueue the trigger in a pending-triggers buffer keyed by controller.
- Extend the pre-priority procedure built in `TASK_0104`: after the SBA loop reports "no actions performed", drain the pending-triggers buffer onto the stack in APNAP order, then loop again (SBAs may result from triggers resolving later; the procedure itself only needs SBA-then-trigger ordering here).
- Reuse the target selection from `TASK_0304`/`TASK_0305` for triggers that target.
- Add 2-3 canonical cards as YAML: an ETB creature (e.g., Elvish Visionary "draw a card"), an attack trigger, a death trigger.
- Key rules: RX-603.2, RX-603.3, RX-603.3b, RX-117.5.
