## 2. Problem

`TASK_0401` builds mandatory triggered abilities — they trigger, queue, and resolve with no player choice. But optional triggers ("when X, *you may* Y" — Rule 603.5) require the controller to decide whether to use the ability as it is put on the stack. This is a genuine decision point, not a rules-correctness detail: the agent must learn when the "may" is worth it (draw-but-lose-life, pay-a-cost-or-not). Per ADR-010 the pre-AI engine should expose real decision branching, and optional triggers are the highest-value trigger decision for the Phase 8 AI. Without this, every trigger in the pool is forced, and the strategy interface has no path to decline one — adding it later would need a new `IStrategy` hook plus a card.

## 3. Acceptance Criteria

- [ ] An optional trigger ("you may …") prompts its controller for a yes/no decision as it would be put on the stack (Rule 603.5)
- [ ] The decision is made through the `IStrategy` interface (e.g., `IStrategy.DecideOptionalTrigger()`), not an engine default — so `RandomStrategy` and future AI strategies both drive it
- [ ] Declining the optional trigger removes it from the pending buffer without going on the stack; accepting queues it exactly like a mandatory trigger (reuses the `TASK_0401` pipe)
- [ ] An optional trigger with a target only chooses its target after the controller accepts (order: accept → target, reusing `TASK_0304`/`TASK_0305`)
- [ ] At least one canonical "may" trigger card added as YAML (e.g., an ETB "you may draw a card; if you do, lose 1 life")
- [ ] Unit test: strategy accepts an optional trigger → it resolves
- [ ] Unit test: strategy declines an optional trigger → no stack object, no effect

## 4. Implementation Guidance

- The ANTLR grammar parses "you may" into an optional flag on the triggered-ability shape (ADR-009 — all oracle text through the grammar). Keep the flag on the same trigger model `TASK_0401` defines; do not fork a separate type.
- Add the `IStrategy` decision method returning a bool for the optional trigger. Wire it into the pending-buffer drain built in `TASK_0401`: before an optional trigger goes on the stack, call the controller's strategy; on false, drop it.
- `RandomStrategy` returns a random (or always-yes) decision for now — the point is the decision *seam* exists for the AI layer, not clever play.
- Keep the accept-then-target ordering correct so the decision and the target choice are distinct `IStrategy` calls.
- Key rules: RX-603.5 (optional triggers), RX-603.3b (still ordered APNAP among simultaneous triggers before the may-decision per trigger).
