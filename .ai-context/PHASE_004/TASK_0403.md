## 2. Problem

The engine applies game events — combat damage, life changes, effect results — by mutating state directly at the point of application (for example, `GameJudge.ExecuteResolvingCombatDamageStep` writes `.Damage` and `.Life` fields inline, and each effect handler mutates the tabletop inside `ResolveCore`). Replacement effects (Rule 614/615) work by intercepting an event before it happens ("if X would happen, instead Y") and the layer system (Rule 613) shapes continuous effects. Per ADR-014 the full replacement/layer implementation is deferred to a phase after the Phase 6 AI milestone, because it adds rules-correctness weight but negligible AI decision branching. This task adds only the *seam* — a single interception chokepoint that events route through — so the later replacement phase can register handlers without re-plumbing every event-application site. This mirrors the state-based-action seam decision in ADR-012.

## 3. Acceptance Criteria

- [ ] A single event-application chokepoint exists that game events pass through before their effect is applied (Rule 614.1 conceptual interception point)
- [ ] Combat damage application in `GameJudge.ExecuteResolvingCombatDamageStep` routes through the chokepoint instead of mutating `.Damage`/`.Life` inline
- [ ] Effect resolution via `BaseEffectHandler.Resolve` routes its result through the chokepoint
- [ ] The chokepoint holds an ordered, currently-empty list of replacement handlers; with the list empty, behavior is byte-for-byte identical to today (Rule 614 not yet implemented)
- [ ] No replacement or layer logic is implemented — the seam is plumbing only (scope fixed by ADR-014)
- [ ] Unit test: with no registered replacements, an event applies unchanged through the chokepoint (regression guard proving the seam is transparent)
- [ ] Unit test: a throwaway test-only replacement registered on the list can observe and pass through an event (proves the registration hook works without shipping real replacements)

## 4. Implementation Guidance

- Introduce a minimal event abstraction only as far as the current pool needs — a discriminated shape for "damage would be dealt" and "effect would apply" is sufficient. Do not model the full Rule 614 event taxonomy now.
- The chokepoint is the transparent identity function over an empty handler list: `event -> (handlers.Aggregate(event, apply)) -> commit`. With zero handlers it returns the event untouched, so existing behavior and tests are preserved.
- Reuse the event-raising infrastructure introduced by `TASK_0401` (triggers observe events; replacements intercept them — same event source, different subscriber contract). Keep the two contracts distinct: triggers react *after*, replacements modify *before*.
- Do NOT touch the priority loop or the SBA seam — those boundaries are fixed by ADR-012. This seam sits at event application, not at the 117.5 procedure.
- Leave a code comment at the chokepoint pointing to ADR-014 and noting the deferred full 614/615 + 613 work, so a future implementer finds the extension point.
- Key rules: RX-614.1, RX-614.5, RX-616 (future — multiple applicable replacements), RX-613 (future — layers).
