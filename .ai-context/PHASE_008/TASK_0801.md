## 2. Problem

The only execution trace today is `ExecutionResult.Messages` — flat strings aggregated up the call stack, neither structured nor queryable. There is no way to see the ordered sequence of what happened inside a phase: which action resolved, what changed zones, when life changed. That blocks both fine-grained debugging (Phase 3-4 stack and trigger ordering is the hardest thing to inspect) and the observability and replay work in `TASK_0802` and `TASK_0803`. This task defines the typed event model only — emission and sinks are `TASK_0802`.

## 3. Acceptance Criteria

- [ ] An event type hierarchy exists with a common envelope (sequence number, turn, phase, logical order — no wall-clock timestamp)
- [ ] Two families are modeled: decision events and outcome events
- [ ] Decision events capture the deciding player, the decision kind, the chosen result by stable identity (entity IDs, not menu index), and the RNG draws consumed (recorded via the tee `IRandomGenerator` decorator from `TASK_0601`)
- [ ] Each decision event carries a request key (turn, phase, player, action index) so replay can assert alignment
- [ ] Outcome events cover at minimum: turn began, phase entered, zone transfer, life changed, damage dealt, permanent tapped or untapped, game ended
- [ ] A state-snapshot event type can carry a whole-tabletop snapshot for coarse views
- [ ] Each event exposes a human-readable rendering so the log message is derived, not hand-written
- [ ] Events are immutable records; no engine logic is added here

## 4. Implementation Guidance

- Model the event hierarchy as sealed records in the contract layer; keep it serialization-friendly (flat fields, IDs not object references) so JSONL in `TASK_0802` is trivial.
- Group under a decision marker and an outcome marker; the request key is a small value type.
- RNG draws are not captured by hand here — they arrive from the recording tee decorator seam in `TASK_0601`; model a draw as a small `(streamId, value)` record on the decision event (or a sibling event).
- Reference the decision points already in the engine: play-order roll and shuffle (`GameSimulator`), priority action (`GameJudge`), attackers and blockers (`GameJudge` combat steps), discard (`GameJudge` ending phase).
- Provide a display formatter per event so `TASK_0802` can drop `ExecutionResult.Messages`.
- Do NOT wire emission or the observer here — that is `TASK_0802`.
