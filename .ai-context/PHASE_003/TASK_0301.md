## 2. Problem

The engine has no stack. Spells and abilities take effect immediately when an action is queued, so there is no window for responses and no LIFO ordering. The stack (Rule 405) is the object that holds spells and abilities while they wait to resolve, and it is the substrate every later Phase 3/4 system builds on: instants respond on it, targeting is checked against it, triggers are placed on it.

This task builds only the data structure and the cast-time push — resolution semantics are `TASK_0302`.

## 3. Acceptance Criteria

- [ ] A stack object exists on `ITabletop` as a LIFO collection of stack objects
- [ ] Casting a spell puts a stack object onto the stack (Rule 405.1) rather than applying it immediately
- [ ] Activating a non-mana ability puts a stack object onto the stack
- [ ] Mana abilities do NOT use the stack — they take effect immediately (Rule 405.6c, 605.3b)
- [ ] A stack object records its source, controller, and (placeholder) target slot for `TASK_0304`
- [ ] The stack is inspectable (top object, ordered contents) for the priority loop and future `GetLegalActions()`
- [ ] Existing tests still pass (the current immediate-effect path is preserved for anything not yet routed through the stack)

## 4. Implementation Guidance

- Add a stack collection to `ITabletop` (e.g., an ordered `IStack` of stack objects). Model a `StackObject` that wraps a spell or ability with its controller and target placeholder.
- The `ActionJudge.QueueAction` path already partially models "queue then resolve" — repoint it to push a `StackObject` instead of resolving inline.
- Keep the mana-ability bypass explicit: mana abilities resolve where they are activated and never create a `StackObject`.
- Do not implement resolution here — leave a clear seam (`TASK_0302` pops and resolves). A pushed object with no resolver is expected at the end of this task.
- Key rules: RX-405.1, RX-405.6c, RX-605.3b.
